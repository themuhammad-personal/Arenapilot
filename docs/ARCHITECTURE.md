# Architecture

ArenaPilot (`com.arenadeck.app`) is a native Android app around the **official**
[arena.ai](https://arena.ai) Direct Chat. Instead of re-implementing a private API,
it loads `arena.ai` in a WebView and injects the engine, which adds every feature on
top of the real page. The protocol, sign-in, anti-bot checks and model behaviour stay
exactly what arena.ai ships. For chat, the official page itself remains the single
visible conversation surface: N0 improves it in place with an Arena-only mobile skin.
There is deliberately no parallel Compose chat shell ([roadmap](arena/ROADMAP-4-BN.md)).

```
┌──────────────────────────── MainActivity ───────────────────────────┐
│ system splash ─▶ BootScreenView (native launch screen, see below)   │
│                                                                     │
│ officialWebView ──▶ https://arena.ai/ (Direct Chat)                  │
│   onPageStarted/onPageFinished ─▶ MainFrameTracker (main frame only)│
│        bridge trust (trustedPage) + engine injection gate           │
│   injectBdsScripts():                                               │
│        1. sd-site.js    site profile (which chat site is this?)     │
│        2. injected.js   network hooks (prompt injection, tool tags) │
│        3. content.css + our-skin.css  engine styles (style#bds-css) │
│        4. content.js    engine UI + logic (Svelte)                  │
│        5. sd-native.js  bridge fetch wrapper, blobs, MCP glue       │
│        6. sd-agent.js   Linux-sandbox agent loop (MCP server)       │
│        7. sd-sheets.js  draggable engine sheets                     │
```

## Layers

| Layer | Where | Responsibility |
|---|---|---|
| Native shell | `android/app/src/main/java/com/superdeepseek/app/` | WebView setup, splash/boot overlay, insets, back handling, file chooser, external links |
| Site profile | `Site.kt` (native twin of `bds/sd-site.js`) | Which chat site this build wraps: trusted hosts, base/new-chat URLs, conversation path, in-app hosts, composer selectors |
| Bridge | `WebViewBridge.kt` | `window.AndroidBridge`: persistent storage, native pickers, blob downloads, haptics, CORS-free fetch for MCP/web tools |
| Engine | `android/app/src/main/bds-assets/bds/` | `sd-site.js` (site profile), `content.js` (UI + features), `content.css`, `injected.js` (network layer), `sandbox.*` (isolated code runners) |
| Polish | `UiPolish.kt` | Small, unit-tested DOM sweep: hides voice / Deep Code entries and repairs raw labels |
| Updates | `UpdateChecker.kt` | Polls this repository's GitHub Releases (stable or beta channel) and installs the signed APK |

The application id is `com.arenadeck.app`; the Kotlin namespace is the historical
`com.superdeepseek.app` (renaming it is churn with zero user value — the class
name resolves against the namespace, not the id). Keep the id and the keystore
unchanged from now on, or updates break.

### One app, one source set

Until the 2026-10-15 cleanup this repo built two apps (Super DeepSeek and
ArenaPilot) from one codebase through the `site` product-flavor dimension. The
flavor system is gone: **ArenaPilot is the one app**, everything lives in
`android/app/src/main`, and `defaultConfig` sets the identity directly
(`applicationId com.arenadeck.app`, `SITE_ID "arena"`, deep-link host
`arena.ai`). `Site.kt` still turns `SITE_ID` into a `SiteProfile`, and still
carries both profiles — the DeepSeek profile remains as a data fixture for the
unit tests and as the description of the engine's other site branch — but only
the arena profile is ever built. Every site-coupled decision on the native side
(bridge trust, engine injection, blob serving, mic capture, external-link
routing, crash/process restore, the composer lookup shared with `UiPolish`)
reads that profile instead of a hardcoded host. The engine does the same thing
in JS through `sd-site.js`, keyed on `location.host`, so the two sides can never
disagree about which site they are on.

What used to live in `src/arenaDeck` now lives in `main` directly:

- the ArenaPilot name, boot title, notice strings and launcher art
  (`mipmap-*/ic_launcher_foreground.png`, `drawable-nodpi/app_icon.png`, all
  generated by `tools/icon/arena_deck_icon.py`, which writes to `main/res`);
  the adaptive-icon backdrop colour `launcher_background`. The artwork honours
  two constraints: every card corner sits inside the adaptive icon's 66dp safe
  circle, and the boot icon is a full-bleed opaque square — `BootScreenView`
  clips it to its own rounded tile (inset 5.8 %, radius 21.2 %).
- `IndependenceNotice.kt`: a one-time "independent app, not affiliated with,
  endorsed by or sponsored by arena.ai" dialog, shown once the launch screen
  has played and recorded as seen only when the user dismisses it. The notice
  strings are `translatable="false"`; each locale keeps only the app name.
- the emoji2 startup removal from the old flavor manifest (merged into the main
  `AndroidManifest.xml`'s `InitializationProvider`): do not acquire a GMS
  downloadable-emoji font at startup — Android kills dependent clients when
  that provider dies (observed in CI run 38510532054).

`engine-arena-branding.test.mjs` pins all of it, including that no flavor
source set ever comes back.

### How the app is proven in CI

The real debug APK is booted on an API-34 emulator by
`android/ci/emulator-smoke.sh`:

- **What is inside the APK** — `android/ci/apk_check.py` reads the built APK itself:
  package, launcher label and activity (`aapt dump badging`), and every launcher PNG
  *pixel for pixel* (decoded, so aapt2's lossless re-encoding cannot fool it).
- **The launch** — the process survives, no crash/ANR, the app opens arena.ai
  (and must never open `chat.deepseek.com`), and the independence notice: it shows
  on the first launch, accepts "OK", and does not show on the second (so "seen"
  persisted).
- **Inside the page** (debug build only) — `android/ci/cdp_probe.mjs`
  attaches to the WebView over the Chrome DevTools protocol and reports what the engine
  found on the real arena.ai page: engine state (injected? rail and "+" sheet mounted? did
  the health check raise its notice?), DOM snapshots through the capture kit, the "+"
  sheet opened with a real pointer click, and the page-load traffic as shapes. It is a
  probe, never a gate. The result goes to `cdp-capture.json` and — because artifacts
  cannot be downloaded from a sandbox — to annotations: GitHub shows ~4 KB per annotation
  and allows ten per step, so a summary comes from the smoke step and the gzip+base64
  capture from its own step (`--report`).

The scripts are tested offline: `engine-arena-ci.test.mjs` runs the real smoke script
against a fake `adb`, `engine-arena-cdp.test.mjs` runs the real probe against a fake
DevTools server (HTTP + WebSocket) whose "page" is a vm running the real capture kit.

### What DeepSeek's services may and may not do on an arena page

On arena.ai the engine must not call DeepSeek's own services or read credentials:

- the **status monitor** (`status.deepseek.com`) and the boot-time **pricing fetch**
  (`api-docs.deepseek.com`) start unconditionally at boot; both are guarded with
  `sdsIsArena()` (an empty `api.statusUrl` means "use DeepSeek's", and the pricing URL is
  a constant, so neither could be switched off through the profile — and
  `features.*` flags are not read by the bundle at all). `engine-arena-services.test.mjs`
  also counts every `deepseek.com` URL in `content.js`, so a new one cannot slip in;
- `injected.js` looks for a bearer token in storage and in request headers (for its own
  history fetch). On arena it reads and keeps none: arena authenticates with cookies, and
  its history endpoint is unknown.

## Capturing ground truth from the real site

`tools/arena-capture/` records the *structure* of arena.ai (never text, titles, tokens,
cookies or ids) so the profile's MODELLED values can be replaced by facts: `capture.js`
(console or bookmarklet), `README-BN.md` (how, in Bengali) and `make-bookmarklet.mjs`.
`engine-arena-capture.test.mjs` asserts the privacy promises, not just the shapes.

## The engine bundle

The engine is a patched, pre-built bundle committed to the repo. It began as the
open-source [better-deepseek](https://github.com/EdgeTypE/better-deepseek) extension and
now carries this project's own UI, mobile layouts, Bengali translations and fixes, so
**never overwrite it with an upstream build**. `scripts/bds-sync.sh` can diff it against
upstream in dry-run mode.

Things inside the bundle that deliberately keep their original names:

- the parser still accepts the old `<BetterDeepSeek>` context wrapper and `BDS:` tool tags
  found in older conversations (new messages use `<SuperDeepSeek>` and `SDS:`); stored
  skills, memories and custom prompts are renamed once on first start
  (`sdsRebrandStored`);
- storage keys (`bds_*`) and CSS classes (`bds-*`), so user data survives updates;
- the third-party DeepSeek Harness *Better DeepSeek Bridge* plugin and its endpoints.

### The site-profile seam (`sd-site.js`)

All of the engine's site knowledge — DOM selectors, API paths, URL patterns,
model detection and pricing — lives in ONE built-in config object inside
`content.js` (the `PH` literal). Almost every reader touches that object
directly; the config service's `getConfig()` is used in only a handful of
places, and its remote-config merge builds a *new* object, so a runtime config
push cannot retarget the engine.

`sd-site.js` (injected first) therefore owns a two-token seam in the bundle:

```js
PH=(window.__sdProfile||function(x){return x})({ features: …, selectors: …, api: … })
```

`__sdProfile` deep-merges the active site's profile INTO that same object, in
place, so every direct reader sees the site's values.

- **chat.deepseek.com — and any host the profile does not know — get an EMPTY
  profile: `__sdProfile` returns the built-in object itself (identity, not a
  copy).** The DeepSeek build is therefore bit-for-bit the engine that shipped
  before the seam existed.
- `arena.ai` (Direct Chat) is the second profile; see
  [docs/arena/PLAN-BN.md](arena/PLAN-BN.md) for the port plan and what is
  verified versus modelled.

Two things the bundle used to hardcode cannot come from that object: URLs it
navigates to and the API paths `injected.js` hooks (it runs *before* `content.js`
and has no handle on the config). `sd-site.js` therefore also resolves them into
`window.__sdUrl` (`home`, `session`, `atHome(url)`) and `window.__sdApi`
(`sessionFetch`, `historyMessages`, `completion`, `completionPaths`, `firstTurn`,
`explicitHistory`). Every call site keeps the DeepSeek literal as a `||`
fallback, so a bundle staged without `sd-site.js` behaves exactly as it did
before the seam existed.

**What `injected.js` rewrites.** It wraps `fetch`/XHR and, for a request on one of
`completionPaths`, puts the engine's system prompt, memories, skills and tool-tag
instructions in front of the user's text — the basis of the high features. It
knows three body shapes: DeepSeek's `prompt` string (the web chat), an OpenAI-style
`messages[]`, and — only when `__sdSite.id === 'arena'` — arena Direct Chat's
`{id, userMessage:{content}, …}`, sent to `create-evaluation` for the first turn
and `post-to-evaluation/{id}` after it (`__sdApi.firstTurn` names the first one).
The arena branch mirrors the `prompt` branch: same injection rules, the
conversation id is the body's `id`, and nothing but `userMessage.content` is
touched; the page's own `content-type` (arena posts JSON as `text/plain`) is kept.
Any other shape passes through byte for byte. `engine-injected-payload.test.mjs`
runs the real `injected.js` in a vm and pins both: DeepSeek's output is golden
(captured before the arena branch existed), arena's is asserted field by field.

"Off" values use sentinels, never empty strings: `querySelector('')` throws,
`DOMTokenList.add/remove('')` throws, and `text.includes('')` matches
*everything* — an empty match string would hide every drawer row instead of one.
`OFF = '.sds-off'` (valid CSS, never rendered) and `OFF_TEXT = '__sds_off__'`
are asserted by the tests.

`engine-arena-coverage.test.mjs` walks all 148 leaves of the built-in config and
requires each one to be either overridden by the profile, owner-protected,
provably unread by the bundle (its key appears exactly once in 3.3 MB — only in
the config literal), inert (a DeepSeek CSS-module hash or a DeepSeek-model-keyed
entry that arena can never match), or neutral (site-independent engine
behaviour). An unclassified leaf fails the test and is printed, so a future
bundle sync cannot quietly ship a DeepSeek selector into the arena build.

`engine-site-profile.test.mjs` pins all of it: the seam's anchor strings must
appear exactly once (a bundle edit that drops the seam fails the suite), the
AST must show `PH` wrapped by `window.__sdProfile||function(x){return x}`,
DeepSeek/unknown hosts must get identity, and no profile may mention
`features.attachMenu` or `features.sideBarMenuInjector` — the "+" sheet's card
set and the sidebar *Advanced settings* entry are owner-pinned surfaces.

### The settings entry on arena (`Phase 4`)

The settings drawer has exactly one door everywhere in the app: a row the engine
inserts into the **account menu** (`WQ()`, reachable only through the
`bds:open-drawer` event it dispatches — there is no native menu item and no other
dispatcher in the bundle). DeepSeek's menu is `.ds-dropdown-menu`, and the
installer (`Y2t()`) only ever scans for that class, so on arena — whose menu is
role-based — the row was never injected and the drawer would have been
unreachable.

`content.js` therefore carries a second, **arena-only** installer beside it
(`sdsArenaInstall()`, called from boot as `Y2t(),sdsArenaInstall(),gge()`). It
watches for `[role="menu"]` on taps and mutations, and `WQ()` dispatches into it
when `window.__sdSite.id === 'arena'`. The row is built by the shipped `rw()` with
the shipped icon, so the label, icon and event are the same on both sites; only
the marker class (`bds-arena-menu-option`) and the `role="menuitem"` attribute are
added. On DeepSeek and in any build without `sd-site.js`, every one of those
functions returns without touching a thing — asserted by
`engine-arena-settings-entry.test.mjs`, which runs the shipped functions against a
fake DOM.

Because a MODELLED menu anchor can silently stop matching, arena also gets a
permanent engine-owned rail (`#bds-settings-rail`). It lives inside `#bds-root`,
so every guard that asks `el.closest('#bds-root')` already treats it as ours, and
it needs no arena selector at all. Its class deliberately does **not** match the
overlay pattern in the back-gesture code (`ROOT_RE`), otherwise `sd-sheets.js`
would read it as a sheet under the finger — a test pins that too.

## Linux sandbox and the agent

| Piece | Where | Role |
|---|---|---|
| `Sandbox.kt` | native | Alpine minirootfs under `noBackupFilesDir/sandbox`, run through `libproot.so` from `nativeLibraryDir` (Termux proot + its libraries, fetched and SHA-checked by `scripts/fetch_sandbox_deps.py` in CI) |
| `SandboxTools.kt` | native | The MCP-shaped tools: `run`, `job`, `read_file`, `write_file`, `edit_file`, `list_dir`, `install_packages`, `preview`, `export_file`, `status` |
| `SandboxService.kt` | native | Foreground service (`specialUse`) with a Stop action, kept while a command runs **or** the agent loop is active (`AndroidBridge.sandboxAgentActive`) |
| `StudioActivity.kt` | native | Linux Studio: terminal, files (viewer with Preview / Ask the AI / Share / Save), preview, settings; shows the AI's commands and file writes live |
| `StudioPreview.kt` | native | Preview of workspace files at `https://workspace.invalid/<guest path>` (served by `shouldInterceptRequest`, never a real host): folders, HTML with relative assets, Markdown (safe renderer), images, video, audio |
| `StudioSheet.kt` | native | Studio's bottom sheets: slide up, drag down (or fling, tap outside, Back) to dismiss |
| `ShellProtocol.kt` | native | Studio terminal ↔ shell: end-of-command markers (exit code, folder), Run/Stop state |
| `sd-agent.js` | engine | Exposes the sandbox to the engine as MCP server `sandbox`, re-reads exact tool arguments from the chat history, the Stop chip, the "ask" mode, continuity (re-scans a finished reply for missed tool calls and nudges a reply that stopped mid-task, at most twice per user message; switchable; reply-end detection uses the poll edge, a thread-growth stall and `bds:token-usage` so short replies are never missed), the **"Continue task?" chip** when the run-once gate stalls after a reload/crash (a tap sends a budget-free continuation nudge), the scroll guard (never pulls a reader who scrolled up back to the bottom), the live sandbox state line in the MCP prompt (`promptContext()` ← `AndroidBridge.sandboxContext()`), and the **Linux & Agent** settings page — its own row on the Advanced settings overview (content.js `sdBuildOverview` → page `linux` → `sdMountLinux` → `__sdAgent.mountSettings`, `#sd-linux-page`; prefs `sd_sandbox_enabled` / `sd_sandbox_mode` / `sd_agent_autocontinue`, shared with Linux Studio; the engine language is mirrored to `sd_ui_locale` so Studio follows it) |
| `sd-sheets.js` | engine | The engine's bottom sheets (+ menu, projects, settings drawer) follow the finger: drag down or fling to dismiss |
| `sd-health.js` | engine | DOM drift guard (risk §4.1): landmark checks every 4 s (composer/message chain, roles, send button); on a drifted page a one-time dismissible notice (EN+BN, `#sd-health-notice`, `sd_health_notice` storage) says chat keeps working while engine extras rest. Site-aware: on arena.ai the contracts are read from the engine's own profile (`__sdSite.profile`) and the notice is branded for ArenaPilot; elsewhere the DeepSeek contracts are unchanged |

The engine does the agent loop itself: the model writes
`<SDS:AUTO:MCP url="sandbox" tool="run">{…}</SDS:AUTO:MCP>`, the engine calls the tool and
sends the result back as the next message. For long tasks the app keeps the renderer at
foreground priority, reloads a page that stops answering after the app returns
(`probePageLiveness`), and after a renderer crash or process restore reopens the same
conversation (`ChatUrls`).

## Slash commands

Typing `/` in the composer opens the command popup.

- Choosing an item only **fills the composer** (`/help `, `/export `…); nothing runs yet.
- A command runs when it is **sent** — Enter on a keyboard, or the send button, which
  is intercepted in the capture phase before DeepSeek's own handler.
- Unknown `/text` is sent to the AI unchanged.
- `/new` and `/compress` switch chats through DeepSeek's own new-chat control, so the
  page is never reloaded (a reload would briefly show the un-enhanced official page).

## Page lifecycle

The engine is injected on every `onPageFinished` of the **main frame** at
`chat.deepseek.com` — `MainFrameTracker` reads the WebView's own URL so iframe
navigations (OAuth, hCaptcha) can neither receive the engine nor flip
`bridge.trustedPage` (which gates storage, files, fetch/MCP and the sandbox).
In-app navigation (DeepSeek is a single-page app) keeps the engine alive; a full
reload re-injects it (the agent's run-once gate then offers the Continue-task
chip instead of silently stalling). Debug builds enable
`WebView.setWebContentsDebuggingEnabled` for `chrome://inspect`; release builds
keep it off.

## Launch screen

`BootScreenView` is a single native view drawn on the Canvas, in the chat's own dark
palette: the page's dark background colour (measured on an earlier run and remembered,
see below) with a soft vignette, a slow star field and an occasional faint shooting star,
the app icon with a faint brand-blue glow, and the Sora wordmark. The wordmark **is the
progress indicator**: its letters rise in dim, then fill with light from left to right
while the page loads, with a soft blue glow on the moving edge. The fill approaches 92%
and waits; it only completes when the page is ready. It is timed from its own frame
clock, so it plays even when the user has turned system animations off. The system
splash hands over on the first frame (same colour, icon in the same place).

The screen is released only when the enhanced page is really on screen, never on a
timer alone:

1. `onPageFinished` injects the engine and starts polling `READY_PROBE_JS` every 300 ms.
   The probe needs the engine CSS (`style#bds-css`), a fully-run `content.js`
   (`window.__sdHandleBack`) and a visible composer or sign-in field.
2. The probe must pass **and** `AndroidBridge.onUiPolished()` must have fired, or 3 s must
   have passed since `onPageFinished` if the polish signal never comes.
3. The wordmark fills to the end, a light sweeps across it and the screen fades into
   the chat. A minimum intro of 2 s keeps a fast (cached) launch from cutting the
   animation short.

The hard cap is 18 s (`BOOT_FORCE_DISMISS_MS`), so a stalled network can never trap the
user on the launch screen.

## System bars

The WebView stays inside the safe area (the root layout is padded by the status and
navigation bar insets), so DeepSeek's header buttons keep their position. The strips
behind the bars take the page's own colour, and the bar icons switch between light and
dark for contrast.

The colour is **measured on screen**: `PixelCopy` copies a 2 dp strip just inside the
top and the bottom edge of the page, and the dominant colour of each strip
(`dominantColor`) becomes the status bar and the navigation bar colour (opaque, with the
system contrast scrims turned off). Reading computed CSS is not exact enough, because
DeepSeek paints its header with gradient fade bands and layered surfaces. The bars are
measured again after every touch (drawers, sheets and navigation change the page),
after a light/dark switch (`AndroidBridge.reportTheme()`, which also recolours the bars
at once) and on resume. While the launch screen covers the page, a CSS estimate
(`PAGE_BG_PROBE_JS`) is used and the bars stay transparent over the launch scene.

The measured dark page colour is stored (`sd_ui` preferences), and the next launch
screen is built on it, so the launch screen and the chat share exactly the same
background. It is only stored at trustworthy moments: the fresh page right after the
launch screen, or just after a switch to dark, and never after a touch (an open sheet's
dim scrim must not be mistaken for the page colour).

## Back button

`MainActivity` asks the engine first: it evaluates `window.__sdHandleBack()` (defined at
the end of `content.js`). The helper closes the topmost engine surface — command popup,
dialog, help sheet, or steps a drawer subpage back to the overview — and returns `true`.
Only when it returns `false` does the WebView navigate back (or the app move to the
background on the first page).

## The N0 shell reversal (2026-10-15)

The first N0 attempt built a Jetpack Compose chat shell ON TOP of the running
arena.ai page: the page stayed hidden underneath, and a parallel native UI
(chat/ package + session-core.js bridge) was the app's face. The owner
rejected it after device testing: a separate shell over the main interface is
ineffective and unnecessary — **arena's official interface itself must be made
Android-native and beautiful** (the N0 goal, re-read). The entire shell layer
was removed:

- gone: `chat/` (ChatScreen, ChatViewModel, NativeChatEvents, NativeChatBridge),
  `session-core.js`, its tests, the Compose toolchain in `build.gradle.kts`,
  the web-mode toggle and its floating return button, the N0 UI-driving smoke;
- the app's face is again the full arena.ai page in the WebView, with the
  engine, the independence notice and the launch screen exactly as before.

What survives from that detour (in git history at `9555ca2`…`8ddc82c` if ever
needed): the proven send path (`__sdEngine.sendQuiet` — the engine's own
fill/settle/click/verify loop, which the engine still uses), the verified
arena DOM facts (`.prose` message bodies, `justify-end` user rows, the
composer's model button `button[aria-label*=", model "]`), and the smoke's
launch-death evidence reporting.

The next N0 step: style and reshape the OFFICIAL interface itself — injected
mobile-first Material-3 skin over arena.ai (colors, typography, spacing,
composer, sheets), so the real page looks and feels like a polished Android
app. The owner's clarifications on scope are being collected before that work
starts.

## ArenaPilot functional adapter — 2026-10-14

The initial profile port did not connect the message selectors to the scanner.
`content.js` now has explicit Arena branches for `g1` (message list), `W_`
(role), `Lvt` (mutation tracking), `LQ` (reprocess) and `eF` (tool session key).
Arena rows are normalized into chronological order; native prose is hidden only
when the engine renders a replacement. `sd-agent.js` consumes the same ordered
nodes for reply signatures and finished tool cards. DeepSeek keeps its old paths.

`MT` starts both privacy toggles disabled on Arena. `sdsArenaPrivacyMigration`
sets these safe defaults once for early-preview upgrades without deleting user
data, then preserves later explicit choices. The network boundary independently
fails closed if config is absent or flags are omitted; memory-only opt-in cannot
send multi-prompts, personas, skills, projects or tool schemas. The optional
Arena instructions are `ARENA_PROMPT` in `sd-site.js`, not the legacy DeepSeek
prompt. The compatibility `<SuperDeepSeek>` envelope and `SDS:` tool grammar
remain unchanged. Turning privacy off later cannot retract prior messages.

The Settings entry docks into a recognized semantic sidebar when present and
otherwise into the composer, not a permanent floating rail. The attach mount is
reused across toolbar moves and reconciled after native button/style changes.
Both flows have a Chromium integration gate (`test:harness:arena`), but sidebar
and conversation fixtures still need authenticated live-site confirmation.
